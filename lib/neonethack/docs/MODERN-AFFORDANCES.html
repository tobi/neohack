neohack · game design proposal · 5 September 2026

Let players discover what they can do.

NetHack’s depth should come from decisions in the dungeon. The interface should make the available verbs, known consequences, and next steps easy to discover.

Recommendation: build a shared, perception-based directional action query and a 9×9 neighborhood in the C library. Use them for movement, object menus, target selection, and explanations in every client. Walking into a door should attempt to open it automatically; a discovered lock should surface alternatives.

Deep implementation design → Exact query and neighborhood contracts, a selectable 9×9 illustration, spoiler-equivalence cases, movement edge cases, fresh native/WASM probes, and the implementation sequence.

First slice: directional actions + neighborhood → locked-door recovery → object actions. These address the clearest friction in the current client and establish reusable library support.

This is a proposal, not a statement of implemented capabilities. “Low downside” means reducing command discovery and input mistakes; it does not mean making risky game actions safe.

Walk into a door. Offer help when it is locked.

Ordinary movement into a perceived closed door should keep the engine’s automatic opening attempt. Do not interrupt it with a menu. If the attempt reveals a lock, return the witnessed reason and sensible alternatives for that square: Use a tool… · Kick · Back. A resisting but unlocked door can instead offer Try opening again. Those are different outcomes.

Use a tool offers eligible perceived items by their real IDs. Call it Try unlocking only when the player has learned that the door is locked; using a key on an unlocked door can instead lock it. Kick explains that the attempt may injure you, make noise, or damage property. The player chooses every attempt beyond ordinary auto-opening; no automatic kick, tool selection or repeated opening loop follows a failure.

Show these alternatives in a compact tile panel, allow Escape/back, and require a fresh press so a held movement key cannot select one. A panel of read-only suggestions is not itself a standing engine decision. Selecting a suggestion issues the corresponding named operation with its target bound. Any genuine engine decision still takes priority and must be answered through its existing lifecycle.

Preserve the engine’s movement and turn semantics: auto-opening does not promise that the same input also enters the doorway. A secret door still looks like a wall. A perceived door that is actually a mimic must receive the same preview as an indistinguishable ordinary door. Existing game.move remains the movement operation; this proposal does not require a replacement movement command.

A directional query and a neighborhood snapshot

A proposed read-only session.actions takes target: { direction: "north" } or target: "here". It returns the sensible actions for that perceived square, their explicit targets, known prerequisites and explanations. This is discovery, not a generic action executor. Invoking an action continues to use game.move, game.open, game.kick, game.apply and the other named operations.

Return the same cell information as observation.neighborhood, centered on the character with radius four: 9×9, up to 81 cells. Include it in every full current observation, not just successful moves; an opening, attack, item use, answer or interruption can change nearby possibilities without moving the character. Mark map edges explicitly and make the neighborhood unavailable if the player’s position is unknown. Replace it with each observation rather than merging stale offers.

// Illustrative future response; not today's protocol.
neighborhood: {
  revision: 12,
  levelId: "level-…",
  center: { x: 16, y: 7 },
  radius: 4,
  cells: [{
    dx: 0, dy: 1, x: 16, y: 8,
    knowledge: "current", // or remembered / unknown
    terrain: "closedDoor",
    walkable: null,        // lock state has not been learned
    movementIntent: "attemptOpen",
    actions: [
      { method: "game.move", params: { direction: "south" },
        availability: "attemptable" },
      { method: "game.open", params: { target: { direction: "south" } },
        availability: "attemptable" }
    ]
  }]
}

walkable means traversable according to the player’s knowledge and known movement abilities, including ordinary door opening. It does not mean that moving there is safe, succeeds, or enters the tile in one turn. Use true for known traversable terrain, including a known unlocked door; false for a known obstacle under those abilities; null when the necessary facts are unknown. Cell freshness qualifies every value. Visible occupants and the resulting interaction belong in separate fields: a creature on a floor does not make that terrain a wall.

An untested locked door and an untested unlocked door must return identical data. Both can return walkable: null and an attemptable movement/opening action. Movement is still allowed to try. After a witnessed locked result, the relevant door can become non-walkable for an ordinary walker and offer alternatives. Unknown or stale information must never become a hidden-state pathfinding oracle.

The outer cells describe nearby terrain and contextual possibilities, not eight extra steps the player can execute immediately. Separate relevant here from attemptable from the current position; an ordinary Open for a door four squares away can say outOfReach, without inventing a path to it. Do not filter legitimate directional attempts solely because the remembered map lacks a target. Unknown cells should not acquire feature-specific hints.

What the evidence actually says

I reviewed 20 archived perception logs containing 4,396 frames after deduplicating non-null request IDs together with their revisions within each file. Seventeen files repeat essentially the same short scenario. Two have longer semantic action sequences; one contains 4,002 legacy recordedStep frames reaching turn 3,640. These are development traces, not a representative player study.

The logs contain a failed boulder push reported as noProgress, a discovered locked door, repeated door resistance, and hunger notifications. The semantic subset has 18 blocked frames, 16 with noProgress. These are concrete examples of weak explanations, not a measured prevalence among players. Historical observation.heard repeats recent narration across frames; I used operation-local heard events to locate examples rather than counting every repeated line as a new incident.

A fresh temporary game through today’s native public API, using seed 42 and a dwarven Valkyrie, confirmed the desired automatic-opening foundation: movement into a known closed door returned openedDoor, no positional change, and no decision. The next move entered the doorway. Preserve that behavior and improve recovery from discovered locks. This probe does not establish a universal turn cost for opening doors.

Current engine scenarios provide stronger evidence for item and activity behavior: ambiguous healing potions require identity-safe selection; armor removal/equipping can spend five turns; interrupted eating/studying retains progress; a wait near danger can return zero-turn noProgress; escape and prayer already require explicit consent. Current client inspection also shows that every carried item receives the same ten action buttons, including irrelevant ones.

Archived stores were read only. No archived game was resumed, modified, copied into this report, or used as a test fixture. The fresh study used a temporary store that was removed afterward. Broader recommendations below also use NetHack mechanics visible in the bundled engine source; they are not claims that these logs cover every mechanic.

Proposed library contract and boundaries

One shared implementation. C produces the facts and offers. Native, WASM, TypeScript, and MCP consume the same generated contract. Clients choose layout, shortcuts, sorting and tutorial presentation; they do not derive eligibility from names, glyphs, inventory letters, or private engine state.

Read-only discovery. The proposed session.actions query begins with a direction or “here”; the same resolver can later accept a perceived item ID or cell coordinate with level identity. It returns the observation revision, knowledge freshness, and supported named actions with explicit targets. The neighborhood calls this same resolver rather than maintaining a second set of rules. Querying must spend no turn, consume no events, reserve no gameplay input, advance no RNG, and reveal no additional world knowledge. Repeated queries cannot probe curses, traps, mimic identity, undiscovered locks or other concealed facts.

// Illustrative shape, not today's protocol.
{
  revision: 12,
  subject: { levelId: "level-…", x: 16, y: 8 },
  knowledge: "remembered",
  actions: [{
    method: "game.open",
    params: { target: { direction: "south" } },
    availability: "attemptable",
    cost: { kind: "variable" }
  }]
}

Attemptable is not guaranteed. Distinguish known prerequisites, unknown state, unsupported operations and known inability. Preserve an advanced route to supported unusual actions. Do not call an action impossible merely because it is not in a conventional menu. Some polymorph forms can eat unusual materials or pass through doors: the library needs perceived, form-aware semantics, not a universal food-category rule.

Standing choices remain real protocol decisions. Bind suggestions to direction, level, position, perceived subject and revision. A suggestion invokes a specific named operation only when selected and no decision is pending. A client must never cancel a pending choice and restart an action to continue it. Read-only suggestions do not themselves become standing decisions; any genuine prompt still uses the existing answer/cancel lifecycle.

Validate again at execution. Reading an offer is not a reservation or authorization. Submit normal guarded requests. Changed context requires a refreshed choice, and uncertain results require receipt recovery. Never fall back to an arbitrary item, another tile, another action or an automatic retry.

Compatibility and ownership. Add public schemas, C dispatch metadata, TS types and MCP descriptions through the catalog generator. Advertise new capabilities accurately. New engine perception facts or runtime behavior need matching package/profile handling; old pinned worlds retain their old guarantees. Keep raw developer journals separate from the public player-history feature.

Acceptance scenarios before shipping
  • A fresh public-API game reaches a perceived door. Movement performs the normal automatic opening attempt. A discovered lock offers alternatives without an automatic kick or tool use. Closing the suggestion panel spends no additional turn.
  • The neighborhood and directional query agree at the same revision. Read-only queries do not modify journals; repeated queries cannot learn lock state. An uncertain movement result is recovered by its exact receipt before alternatives can execute.
  • A 9×9 snapshot centers correctly after movement and level changes, handles map boundaries and unknown position, and refreshes after non-movement actions. Distant cells never advertise adjacent-only actions as executable now.
  • Worlds indistinguishable to the player yield indistinguishable offers: trapped versus untrapped doors, unknown lock states, unknown curses and mimic disguises do not alter discovery output. Use controlled engine scenarios for this equivalence check, not private-state access in production.
  • Confusion, blindness, impaired movement, changed form, and stale terrain do not yield false exact targets or guarantees. Known unlocked doors are traversable, untested locks remain unknown, and known form-specific passage is respected.
  • Item menus preserve exact identity after inventory reordering, stack changes and multiple visually identical objects. Known inability is explained; unknown safety is not invented.
  • Target previews and repeated inspection consume no turns or events. A known ally is identified only from actual perception; no guessed beam range, ricochet, hidden creature or hit probability appears.
  • Interrupted food/study offers an explicit valid continuation, spends only the engine’s actual remaining work, and is never resumed by observe, receipt recovery or ordinary wait.
  • Keyboard, pointer and touch clients show the same library offers. Held keys cannot accept a newly opened choice; screen readers announce the target, cost uncertainty and cancellation option.

Exercise native and sandboxed browser paths with new temporary stores, plus the repository checks and generated-schema drift check. The fresh door probe above verifies current behavior only; these proposed-feature scenarios have not been implemented or passed.

Good ideas that need separate design

Autoexplore, click-to-travel, rest-until-healed and bulk search need explicit stop rules, cancellation and per-step durability. Autoeat, autokick, autoequip and auto-answer can spend resources, change tactics, violate conducts or create irreversible harm. Corpse safety scores and “best item” recommendations can leak hidden information or impose a strategy. They do not belong in the first low-downside scope.

Opening a choice on every ordinary move or closed door would be a regression. Keep movement and automatic opening fast; surface alternatives after a discovered obstacle or on deliberate inspection. An unknown walkability value permits an attempt rather than disabling movement.

Command completeness is a separate release requirement. The current catalog lacks named spellcasting, throwing/firing, container looting, paying/chatting, targeted untrapping, engraving and naming/calling. In particular, a Wizard needs discoverable spellcasting. Context menus should expose each as its public operation is implemented and tested; they cannot compensate for missing game verbs by sending raw keys or using a generic action escape hatch.
