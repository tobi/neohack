neonethack · implementation design · 5 September 2026

One world of actions.
Every client can see it.

A read-only directional query and a 9×9 neighborhood should describe the player’s available attempts, using only what the player knows. Normal movement still opens doors. Discovered obstacles get useful alternatives.

← The broader 14-point design review

Design status: implemented in the shared C resolver, public catalog/schemas, SDK and pixel client. Fresh native/WASM scenarios cover revision-bound queries, door evidence, confirmations, replay and exact receipts. A separate temporary test engine varies hidden state to verify perception equivalence. Cell traversal, source-to-target movement and session input permission remain separate facts. The illustrative grid below is a design explanation, not a live game.

1. The product behavior to preserve

  1. Move normally. One movement request retains the engine’s ordinary bump behavior. A door may open; a creature may be attacked; an ally may be displaced. No extra “interact?” question appears on every step.
  2. Explain a discovered obstruction. A locked-door result anchors a small action panel to that door. It offers Use a tool, Kick, and Back. A resistant unlocked door instead offers another opening attempt.
  3. Keep inspection free. Clicking any neighborhood tile opens a description and sensible actions without attempting any of them. Pointer, touch, keyboard and MCP clients use the same offers.
  4. Do not promise success. Availability means an appropriate attempt, not a prediction. A floor can be walkable and dangerous. A visible door can hide a trap. A tool can fail.
  5. Preserve intent. Selecting a menu action binds the perceived square/item and its revision. Old offers cannot quietly retarget themselves when the character moves.

2. Three questions, three answers

QuestionFieldMeaning
Does the known terrain support ordinary traversal?walkable: true | false | nullKnowledge-based terrain traversal for the hero’s known locomotion, including ordinary automatic door opening. Known unlocked doors are true. Untested closed doors are null. This excludes occupant interaction and source-dependent diagonal restrictions.
What would trying to move toward this adjacent square mean?movementThe source-to-target edge: adjacency, known geometric restriction, and the perceived interaction such as step, attempt opening, creature bump or possible push. It may remain unknown.
Can another gameplay request be issued at this boundary?inputGateReady, standing decision, recovery required, ended, or unavailable. This is session-wide. An offer never overrides it.

An intact open doorway illustrates the separation: its terrain is walkable, but diagonal entry can be blocked. A creature on floor leaves the terrain walkable while the bump interaction becomes a creature encounter. A standing warning leaves all terrain facts intact while new gameplay input is unavailable.

No client should disable manual movement merely because walkable is false or null. A player can deliberately test an obstacle. Movement may also trigger a supported interaction such as digging. The field guides presentation and future route planning; it is not a legality guard or a new collision engine.

For water, lava, unusual forms and unknown locomotion, v1 should return null unless the perception contract supplies enough knowledge to make the classification. Show known hazards separately. Do not turn “not a normal walking route” into “the engine cannot let you enter this square.”

4. A concrete public contract

Use session.actions for discovery. Keep all execution in named game.* and decision.* operations. The public C ABI remains the existing JSON request interface; no public engine structs or generic execute-action method are necessary.

{
  "version": 1,
  "method": "session.actions",
  "params": {
    "sessionId": "g-…",
    "expectedRevision": 12,
    "target": { "direction": "north" }
  }
}

The first version accepts the eight compass directions and target: "here". A later extension can accept an explicit level/cell or a perceived item ID through a closed target union. Up/down remain separate from compass directions: stairs are actions on “here,” not cells in a 2D grid.

Require expectedRevision for this query so its result can be associated with the map the user inspected. Reject a mismatch before doing any work. A read-only query does not need a gameplay request ID, does not reserve a receipt, and does not consume the current event stream. Never start or resume an unloaded engine to answer it.

  "kind": "actions",
  "sessionId": "g-…",
  "basis": {
    "revision": 12,
    "levelId": "level-…",
    "origin": { "x": 16, "y": 7 }
  },
  "inputGate": { "state": "ready" },
  "cell": {

    "visible": true,

      "relation": "adjacent",
      "intent": "attemptOpen",
      "knownRestriction": "lockedDoor"
    },
    "actions": [{
      "key": "kick",
      "method": "game.kick",
      "arguments": { "target": { "direction": "north" } },
      "availability": "attemptable",

      "cautions": ["mayInjure", "mayMakeNoise", "mayDamageProperty"]
    }, {
      "key": "apply",
      "method": "game.apply",
      "arguments": {},
      "availability": "needsSelection",
      "nextInput": "item",
      "context": { "kind": "door", "x": 16, "y": 6 },
      "cost": "variable"
    }]
  }
}

Important: context is explanatory context, not an argument to game.apply. The current apply method accepts an item, then may ask for direction and confirmation. Until a separately specified target-bearing tool operation exists, the client must present those decisions. It can highlight the original door but cannot pretend the direction was already passed to the engine.

Action keys identify presentation entries within a response. They are not engine object IDs, decision IDs, authority tokens or an execution API. An action’s argument object is a typed subset of the corresponding generated method parameters; executing it adds a new request ID and the basis revision. Omit request identifiers from read-only offers.

Action fields and availability
  • attemptable: meaningful from the current boundary based on public knowledge. It may fail or produce a warning.
  • needsSelection: a named operation can begin but the player must select an item or target. Starting it is not the same as committing to an arbitrary candidate.
  • outOfReach: this is a relevant interaction with a known distant feature, but the corresponding action cannot target it from here. Such entries have no executable arguments in v1.
  • knownBlocked: a public, specific prerequisite is missing. Include a reason. Do not use hidden curses, object properties, or unseen obstructions to produce this state.
  • uncertain: information is insufficient to make a stronger suggestion. Generic directional attempts remain discoverable.

Use a closed union for these variants so, for example, an out-of-reach interaction cannot accidentally carry a runnable game.open direction. Keep unsupported operations out of live action offers; describe broader capability limits through discovery/help. Relevance and availability do not imply safety, success probability or tactical recommendation.

inputGate is evaluated separately and takes precedence over every entry. With a standing decision, the query may still describe the square, but the only actionable controls are that decision’s supported answers/cancellation. With recovery required, the old grid can be inspected with an explicit stale marker; it must not advertise usable input.

Neighborhood shape, bounds and ordering 
observation.neighborhood = {
  version: 1,
  status: "available",
  basis: { revision, levelId, origin: { x, y } },
  radius: 4,
  inputGate: { state: "ready" },
  cells: [ /* exactly 81 entries, row-major dy=-4..4, dx=-4..4 */ ]
}

// Capability exists, but no current neighborhood is available:
observation.neighborhood = {
  version: 1,
  status: "unavailable",
  reason: "unknownPosition" // or unsupportedPerception / recoveryRequired
}

Use exactly 81 slots for a stable grid. Mark out-of-map positions with inBounds: false, false walkability, no terrain assertion and no actions. Do not turn the map edge into a perceived wall. NetHack’s storage width is 80, but isok excludes column zero; use the engine’s public geometry contract rather than treating all array slots as playable.

Center has movement.relation: "here". The eight neighbors have "adjacent". The outer 72 have "distant"; they have no immediate movement request to their coordinate. Floor-item IDs are usable only where perception actually exposes them. Distant object glyphs do not become item references.

Build every cell from the same resolver as session.actions; the matching query cell must equal its neighborhood cell at the same basis. Fixed ordering and bounded fields make tests and rendering deterministic. The API returns intent, not preformatted buttons or per-client key bindings.

Include the neighborhood on each new full semantic observation, including zero-turn decisions and non-movement operations. Missing on an old receipt means it did not exist there: do not recalculate and attach today’s neighborhood to historical data. Future engine support should be explicit in capability negotiation.

5. Spoiler freedom is a data-flow property

If two worlds are indistinguishable to the player, their action metadata must be indistinguishable too. This covers booleans, reason codes, menu presence, item filtering, preferred action order, text, cost estimates and invalidation. Hiding a field does not help if a button disappears or the response changes when an unseen monster moves.

The implementation should have a narrow input boundary:

Engine perception + witnessed player-facing outcomes
                        ↓
C knowledge snapshot (with evidence and freshness)
                        ↓
Pure C affordance resolver
               ↙                    ↘
session.actions                  neighborhood
                        ↓
Native / WASM / TS / MCP / pixel client

The resolver must not receive live levl, monster lists, object internals, RNG state or engine action functions. It consumes a sanitized knowledge structure. When actor capabilities affect movement, the engine adapter must explicitly identify which capabilities the hero knows; dumping raw intrinsic/extrinsic property bits would reveal unidentified equipment effects.

Do not use test_move as the preview API. Despite its name, it reads live terrain, creatures, boulders and traps; it also resets svc.context.door_opened. Travel modes have their own tactical assumptions. Wrapping it in a “dry run” would neither establish spoiler freedom nor guarantee zero side effects.

Existing eligible_carried is useful reference code but its callers are not automatically safe for discovery. In particular, older-engine inventory refresh paths can send commands. Factor a pure query over already known items; return uncertainty when current information is absent rather than invoking ensure_inventory or ensure_floor.

The equivalence cases that must pass

6. Door knowledge needs its own history

The current map describes open versus closed doors, but a witnessed lock is only an action reason/narration. Seeing a closed door does not tell you whether it is locked. Even when the square is visible, terrain freshness cannot refresh lock knowledge.

Add a bounded, level-and-coordinate knowledge record fed by witnessed outcomes. Suggested facts: perceived door shape/orientation, last observed lock state, and last observation turn. Store knowledge, not an engine door identity or raw doormask. Treat a replaced/disguised feature as whatever the player can distinguish.

Attach witness events at existing engine branches which report the player-facing fact, carrying the actual affected square. Deriving the affected square from the requested direction is unsafe under confusion or other redirection. Do not add a second pass which queries the door’s private state after every input.

A remembered true/false is a claim about last-known traversability, qualified by evidence age. A client planning a route must treat remembered facts as provisional. If the public field is intended to guarantee current facts instead, collapse remembered values to null; do not mix these two definitions across clients. This design chooses last-known values with explicit freshness, matching the existing remembered map.

Persist or deterministically reconstruct this ledger across native restart and WASM reload. A free query cannot write it. Rebuild from the pinned engine’s witnessed events during replay, or use integrity-checked semantic metadata tied to the exact input boundary; never mine a private save for the current hidden lock bits. A map clear is not necessarily a level change, so key records by real level identity and separate redraw handling from knowledge invalidation.

7. Movement and action edge cases

For a release with incomplete actor-perception facts, prefer an honest null and generic attempt to a confident inference. The initial slice does not need exact handling of every polymorph form to be useful. It does need to avoid presenting the ordinary-human assumption as an engine guarantee.

8. A stale offer must stay stale

The wire protocol already has the essential guard: expectedRevision. However, the TypeScript Game.operation wrapper currently supplies this.current.revision when the queued callback runs. That is convenient for sequential key presses but insufficient for a button created from an earlier observation.

// Proposed SDK overload; not implemented.
const offeredRevision = neighborhood.basis.revision;
await game.kick("north", { expectedRevision: offeredRevision });

// Existing low-level equivalent already carries the intended guard:
await api.request("game.kick", {
  sessionId: game.id,
  requestId: newRequestId,
  expectedRevision: offeredRevision,
  target: { direction: "north" }
});

Add optional revision-pinning options to the named SDK methods used by offers. Copy the revision and arguments at invocation; do not silently replace them with the latest state when queued. The usual movement methods can retain their current sequential behavior when no explicit basis is supplied.

On stale rejection, refresh the panel and require another deliberate selection. On lost response, keep the original request and recover its receipt. Do not interpret an unavailable receipt or a new neighborhood as permission to repeat a kick. A historical receipt must not rewind a newer live map.

session.actions adds a distinct response variant to the generated/public TS union. Its SDK helper should serialize with other game work, return the action result, and avoid the accept() path that expects a full snapshot. It must neither clear pendingRequest nor make an unresolved game playable.

9. UX: few decisions, good explanations

  • Ordinary door: perform the normal auto-open attempt and show what happened. Keep focus on movement. Do not add a second automatic step or a retry loop.
  • Locked door: stop held-key input, anchor a compact panel to the actual perceived target, and offer supported alternatives. Opening the panel itself does not advance time.
  • Item/tool selection: use public IDs. Show known applicable tools prominently, and expose the broader supported Apply action without claiming every tool unlocks doors.
  • Target decision: highlight the intended square, but preserve the actual prompt and decision ID. Selecting an item does not consent to every later confirmation.
  • Hover/click: show “Walkable · remembered” or “Closed door · lock unknown,” then the available attempts. A small symbol supplements color for unknown and out-of-reach states.
  • Map rendering: do not turn every uncertain square into a blocked tile. Keep unknown exploration possible. Keep known hazards visually distinct from ordinary walkable terrain.
  • Keyboard/touch: a newly opened panel starts with no action accepted; repeats and queued pointer events cannot trigger it. Back closes suggestions; Cancel answers only an actual cancellable decision.
  • MCP: provide compact structured actions and the same basis/unknown semantics. Agents should not need to interpret English narration to discover a lock or assemble a target.

10. Concrete change map

No startup-time upgrade of existing worlds. The new library can advertise its resolver version, while each session reports whether its pinned engine supplies the needed evidence. Old packages can expose a limited/unknown neighborhood or an explicit unsupported-perception result. Old receipts stay byte-for-byte historical. A changed perception hook still requires matching native pins/WASM artifacts and provenance; whether a new runtime profile is required depends on any changed game behavior or journal compatibility, not merely the addition of a display field.

11. The first shippable slice

  1. Knowledge contract and pure resolver. Define actor-known locomotion and per-fact freshness, add a bounded C knowledge structure, and make the resolver callable without an engine handle. Implement floor, wall, unknown terrain, open/closed doors and ordinary adjacent geometry conservatively.
  2. Witnessed door facts. Emit targeted lock/open/close/resistance facts only where the engine actually discloses them. Preserve them through observation and restart. Prove that hidden lock changes cannot affect the resolver output.
  3. Query and 81-cell neighborhood. Generate the named query schema, response variant, capabilities, TS helper and MCP tool. Add the same resolver output to fresh full frames. Support a clear unavailable state.
  4. Intent-preserving client integration. Pin menu actions to their offered revision, retain normal bump-opening, show alternatives after locked failure, and render the same neighborhood facts for all input methods.
  5. Evidence before broader affordances. Pass real door/diagonal/reload/uncertainty scenarios on native and sandboxed browser backends, plus hidden-state equivalence tests. Then extend item menus, condition help and other recommendations.

This slice does not require pathfinding, autoexploration, a generic action executor, new combat rules or automatic tool use. It also does not yet solve every missing verb. Separately adding a target-bearing unlock operation may reduce prompts, but it needs its own explicit item, target, confirmation and occupation contract.

Keep the grid lightweight: one shared input gate and basis; no repeated inventory in all 81 cells; bounded reason/caution codes; item selection through the query when needed. Benchmark serialization size and p95 latency on native and browser builds before choosing a hard wire-size target. Compute from a snapshot in O(81) cell work plus a bounded inventory summary, without scanning the inventory anew for every cell. Do not claim a measured performance budget before those measurements exist.

12. Validation that proves the claim

  1. Pure resolver: it accepts only the knowledge structure. Deterministic table tests cover three-valued traversal, edge geometry, bounds, ordering and availability variants. These tests verify the contract, not just a copy of the implementation.
  2. Engine adapter equivalence: controlled engine scenarios vary a hidden lock, trap, monster, curse or unobserved ability while preserving the player’s knowledge. Compare all metadata, including shape, order, reasons, visibility and invalidation. Resolve any difference; do not mask it in recordings.
  3. No input/no RNG: query the same frame repeatedly, compare input bytes and revisions, then execute identical commands in two fresh pinned worlds, only one of which was queried. Their subsequent observations and decision sequence must agree. A pure resolver must also have no RNG or engine-action linkage.
  4. Real gameplay: normal auto-open; locked bump and explicit alternative; unlocked-door close/reopen; resistant opening; intact-door diagonal; friendly encounter; a public known hazard; item ambiguity; a current standing decision.
  5. Storage: native cold restart and real IndexedDB browser reload preserve witnessed facts and pending context. Lost response after a real door/tool action returns the exact receipt without repeating the attempt. Corrupt knowledge metadata is reported, never repaired from hidden state.
  6. SDK races: create a button at revision N, perform another action, then activate the old button. It must reject instead of issuing its direction from the new position. An action query must not clear an uncertain request or accept an old frame as current.
  7. Compatibility: query against older pins and compare native/WASM capability discovery. Missing facts produce explicit uncertainty. Previously stored receipts never gain fresh neighborhoods.
  8. Browser use: pointer, keyboard and touch receive the same offers, held inputs cannot accept panels, focus returns predictably, and screen readers announce target/freshness without depending on color.

Implemented checks live in tests/affordance.c, tests/affordance-contracts.mjs, tests/hidden-knowledge.test.mjs and the sandboxed browser suites. The hidden-state test links a temporary engine; its mutation hook is never included in the production engine. Late storage diagnostics override the gate captured in an earlier receipt: preserve that exact receipt and require recovery; fresh observations/queries report current unavailability.

Use new temporary stores. Controlled hidden-state fixtures belong in test setup, never in the production resolver. Run the repository’s native, Node, WASM, browser and generated-schema checks after implementation. The exploratory probes below are current-behavior evidence, not passing tests for the proposed API.

13. Findings from fresh engine probes

These probes used fresh temporary games through public APIs, with human female lawful Valkyries for movement and a human female chaotic Rogue for the tool prompt. Seeds 1–24 were tried until an ordinary and locked doorway were found on each target. Route staging used only perceived floor/door cells and stopped at unexpected decisions. No private save was used. The native input journal was read only to verify observation side effects; all fresh stores were removed.

WASM probes used an explicitly volatile worker for this study, not browser durability testing. Native and WASM happened to agree on these cases; that is not a promise of cross-target seed equivalence. Existing local source changes adding cell visibility were present during review; the native probe lacked that field while the WASM probe supplied it. The affordance design must tolerate such capability differences.

The biggest new implementation requirement is therefore persisted knowledge of what an action revealed. A directional menu built only from today’s terrain.type cannot distinguish a discovered lock from an untested door after the action’s message has passed.
